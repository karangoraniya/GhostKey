GhostKey

Give agents authority, not secrets.

The problem

Agents need real access.
Today, that means real secrets.

  • ✕A GitHub PAT, an AWS key, an API token - handed to code you don't fully control, in full, forever.
  • ✕No scope. If the agent can read one repo, it usually can do a lot more with that same key.
  • ✕No expiry, no revocation path that doesn't mean rotating the credential everywhere else too.
  • ✕No human in the loop when the agent asks for something genuinely high-risk.
The idea

What if the agent never saw the secret at all?

GhostKey gives an agent a random, short-lived capability ID - scoped to one provider, one resource, one action, one expiry. The real credential stays encrypted on a Ledger, and is only ever decrypted on the backend, for the instant it's needed.

Agent→ Ghost Identity→ Capability→ Ledger Trust→ Provider
How it works

Authority, with boundaries.

Two Ledger primitives, one product

A hardware root of trust, not a config file.

KEY RING

Encrypted credential storage

Every GitHub, AWS, and Custom API secret is encrypted with wallet-cli ring. Decrypted only inside the request that needs it - never logged, never returned.

DEVICE + SIGNER KIT

Physical approval

High-risk authority requires a real EIP-712 signature, reviewed and confirmed on a connected Ledger over USB - not a checkbox in a browser.

VERIFIED SERVER-SIDE

Signature-checked, not trusted

The backend recovers the signer with viem and compares it to the pinned device address before minting anything elevated.

What's actually enforced

Validate before decrypt. Every time.

  • ✓Every provider call re-checks policy before decrypting a credential, and again immediately before the outbound request.
  • ✓Failures are always one of a fixed set of error codes - never a raw stack trace or upstream diagnostic.
  • ✓Capabilities are TTL-capped and can never outlive the ghost identity that owns them.
  • ✓Everything lives in process memory. No database - a backend restart clears every grant and credential.

Getting started

Connect your agent in one command.

  1. Run the backend - bun run dev --port 3100, with your Ledger Key Ring set up.
  2. Create an identity and grant a capability in the dashboard - copy the ghost and capability IDs it gives you.
  3. Point your MCP client at it - Claude Code, Cursor, or any MCP-speaking agent.
  4. Ask your agent to use the tools - it only ever receives those capability IDs, never a credential.
claude mcp add ghostkey --transport stdio --scope local \
  --env GHOSTKEY_BROKER_URL=http://127.0.0.1:3100 \
  -- npm --prefix "$PWD" --silent run mcp
What you're about to see

Five steps, one physical confirmation.

  1. Create Agent - a fresh ghost identity, granted a scoped GitHub capability automatically.
  2. Run with GhostKey - a real GitHub issue is created. The agent never touches the credential.
  3. Test Unauthorized Action - the same agent asks for a delete. Blocked before any request is sent.
  4. Request Authority - the agent asks for github.admin.write. A pending request is created, not a grant.
  5. Approve with Ledger - a physical signature on the device. Only then is temporary elevated authority minted.
